# Changelog

## Unreleased

PII retention and application-owned core PII activation ([#38](https://github.com/redact-secret/redact-secret-reversible/issues/38), per the [decision record](docs/decisions/2026-09-27-decide-pii-retention-and-activation-ownership.md)). The supported core is now `@redact-secret/core@0.1.0-beta.10` exactly ([#41](https://github.com/redact-secret/redact-secret-reversible/issues/41)).

- **Core compatibility ([#41](https://github.com/redact-secret/redact-secret-reversible/issues/41)):** `@redact-secret/vault` and `@redact-secret/vault-server` peer-depend on `@redact-secret/core` `0.1.0-beta.10` exactly, and the Python bridge's `PINNED_CORE_VERSION` is `0.1.0-beta.10`. `@redact-secret/vault@0.1.0-alpha.1` stays the release for `0.1.0-beta.9`. Runtime PII feature detection is unchanged, so a core without PII support still gets the fail-closed rules below.
- **Behavior change (breaking) on core beta.10:** `createVault()` and `startVaultWorkerHost()` without `pii` no longer initialize the core. They adopt the activation the application already set, and fail with `CORE_FAILURE` / `coreCode: "NOT_INITIALIZED"` when nothing initialized the core. `createServerVault()` without `pii` fails the same way (`VAULT_FAILURE` / `vaultCode: "CORE_FAILURE"` / `coreCode: "NOT_INITIALIZED"`). Migration: pass `createVault({ pii: [] })` (PII off; likewise `startVaultWorkerHost({ pii: [] })` and `createServerVault({ ..., pii: [] })`), or await the core's `initialize(...)` before creating the vault. The Python `NodeCoreBridge` is unaffected: it always initializes its own bridge process, with `pii=[]` by default.
- `@redact-secret/vault`: `CaptureOptions.pii: { retain }` is an exact-type allowlist. A `redact` finding whose type starts `pii_` is never retained unless its type is listed. `eligible` can narrow that list but cannot widen it.
- `@redact-secret/vault`: `VaultOptions.pii` (forwarded to the core's `initialize({ pii })`) and `VaultOptions.expectPiiActivation`. `Vault.piiActivation` reports the observed identity, or `null` when the core has no PII support. PII support is detected at runtime from the core's `piiActivation` export.
- `@redact-secret/vault`: new error codes `PII_UNAVAILABLE` and `PII_ACTIVATION_MISMATCH`.
- `@redact-secret/vault-server`: forwards `pii`, `expectPiiActivation`, and capture `pii` to the vault. Adds `ServerVault.piiActivation` and `VaultServerError.coreCode` (the core's code behind a `VAULT_FAILURE` / `CORE_FAILURE`).
- `redact-secret-vault-server` (Python, [#40](https://github.com/redact-secret/redact-secret-reversible/issues/40)): `NodeCoreBridge(pii=..., expected_pii_activation=...)` forwards the selection to the core's `initialize({ pii })` in each bridge process, reports `CoreScanOutcome.pii_activation` (`None` without PII support), and pins the identity across scans (`PII_ACTIVATION_MISMATCH`). `CaptureOptions.pii=PiiRetention(retain=...)` follows the same allowlist rules, with new error codes `PII_UNAVAILABLE` and `PII_ACTIVATION_MISMATCH`; bridge responses are now parsed strictly.
- On a core without PII support (beta.9), callers that pass no PII option see no behavior change. Any PII option fails closed with `PII_UNAVAILABLE`, and `pii: []` equals omission.
- `@redact-secret/vault` Worker mode ([#39](https://github.com/redact-secret/redact-secret-reversible/issues/39)): protocol version 2 (a version-1 peer is rejected with `WORKER_PROTOCOL_VIOLATION`). `startVaultWorkerHost({ pii, expectPiiActivation })` activates or adopts inside the Worker realm, `vault-ready` and `WorkerVault.piiActivation` report the observed identity, `createWorkerVault(worker, { expectPiiActivation })` rejects with `PII_ACTIVATION_MISMATCH`, and Worker `capture` accepts `pii: { retain }`, validated on both sides. No page message can carry PII selectors. `VaultError` is now exported from `@redact-secret/vault/worker`, as the README already documented.
- All three surfaces now carry PII activation and retention: the main-thread vault and `@redact-secret/vault-server` ([#38](https://github.com/redact-secret/redact-secret-reversible/issues/38)), Worker mode ([#39](https://github.com/redact-secret/redact-secret-reversible/issues/39)), and the Python bridge ([#40](https://github.com/redact-secret/redact-secret-reversible/issues/40)). The PII-on qualification matrix against the published core is [#42](https://github.com/redact-secret/redact-secret-reversible/issues/42).

## @redact-secret/vault 0.1.0-alpha.1

First alpha. In-memory, whole-input capture and structured-field restoration for Node.js and browser main-thread runtimes, against `@redact-secret/core@0.1.0-beta.9` exactly.

- `createVault` with bounded entries, retained bytes, value size, input size, findings, entry TTL, vault lifetime, and restore size.
- `capture` gates on core actions (`block` aborts, `warn`/`allow` rejected unless `unredacted: "pass-through"`), issues 128-bit `<rsv_…>` tokens, refuses token-like input literals, and commits only after output validation.
- `restore` into application-granted `sink` + exact `path` pairs, with whole-request preflight, per-entry use budgets (default 1), a page-local `releasePolicy`, and fail-closed handling of altered tokens.
- `revoke`, `dispose`, `stats`, sanitized `VaultError` codes, and safe-metadata audit events.
- Not included: Worker mode, server authorization, persistence, streaming, and free-text restore.
