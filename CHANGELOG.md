# Changelog

## Unreleased

### Python

**Not released.** `redact-secret-vault` stays at `0.1.0b3` on PyPI.

- `redact-secret-vault` (Python): `python -m redact_secret_vault doctor [--node-modules PATH]` ([#135](https://github.com/redact-secret/redact-secret-vault/issues/135)) checks the `node` executable, where the core is loaded from, that it loads, and that it is the pinned version, and prints a fix for each failure. It exits 1 if a check fails and prints no finding value. The version is still `0.1.0b3`; this is not on PyPI.

### Python persistence groundwork

**Not released. Python persistence is not implemented and not supported.** `redact-secret-vault` stays at `0.1.0b3`, with no runtime dependency in the base install. These entries are internal modules under the [plan](docs/plans/python-persistence-parity.md); support is stated only by the qualification record of [#128](https://github.com/redact-secret/redact-secret-vault/issues/128). Decisions: [record](docs/decisions/python-persistence-api-and-packaging.md).

- `redact_secret_vault.persistent` ([#119](https://github.com/redact-secret/redact-secret-vault/issues/119)): contracts, errors, limits, and validators mirroring `@redact-secret/vault-contracts`, standard library only. Needs Python 3.11 or later; the in-memory server is unchanged.
- `redact_secret_vault.persistent` ([#120](https://github.com/redact-secret/redact-secret-vault/issues/120)): canonical encoding of the entry identifier, associated data, payload, and envelope framing; the session tag and request digest. Standard library only. The `entryId`, AAD, payload, envelope-framing, request-digest, and session-tag groups of [`conformance/persistent/v1/vectors.json`](conformance/persistent/v1/vectors.json) are reproduced byte for byte, and every negative case of the envelope and payload decoders is rejected with the listed code. [`verify_vectors.py`](conformance/persistent/v1/verify_vectors.py) is kept as the independent cross-check (see the decision record).
- `redact-secret-vault` ([#121](https://github.com/redact-secret/redact-secret-vault/issues/121)): extras `crypto` (`cryptography>=47`), `postgres` (`psycopg>=3.2,<4`), and `aws-kms` (`boto3>=1.43`), one distribution. The base install still has no runtime dependency. Modules `redact_secret_vault.crypto`, `.stores.postgres`, and `.keys.aws_kms` are skeletons that raise `ImportError` naming the extra when its dependency is missing. New CI job `python-wheel` builds the wheel and checks, in clean virtualenvs outside the repository, that the base install lists no third-party distribution and that importing one optional module loads no other family's dependency.
- `redact_secret_vault.crypto` ([#122](https://github.com/redact-secret/redact-secret-vault/issues/122)), behind the `crypto` extra: `create_record_crypto` (a `RecordCrypto` over any `KeyProvider`: HKDF-SHA-256 entry keys, AES-256-GCM, duplicate-entry and mismatched-binding rejection, no nonce parameter) and `create_local_key_provider` (active, decrypt-only, and retired keys over bytes in process memory, explicit scope; profile `local-bytes-hkdf-aes-256-gcm-v1`). Keys and decrypted payloads live in `bytearray` buffers that are overwritten on every path; errors carry no `__cause__` or `__context__`. The entry-key, envelope, and local-provider vector groups are reproduced and every negative case is rejected with the listed code. No thread offloading; measured times are in the [decision record](docs/decisions/python-persistence-api-and-packaging.md).
- Conformance ([#123](https://github.com/redact-secret/redact-secret-vault/issues/123)): [`conformance/persistent/v1/schedules.json`](conformance/persistent/v1/SCHEDULES.md), the store cases of `@redact-secret/vault-conformance` as language-neutral data (97 converted, plus 7 fault cases and 15 server-level cases), an orchestrator that drives a driver over standard input and output, and a JavaScript driver for `@redact-secret/store-memory`. The hold and fault vocabulary is fixed. For `store-memory` the schedules and the native harness agree case by case in four configurations, and the harness's own mutants fail the matching schedules. The three aliasing cases and the seeded random sequences stay native. No Python code in this entry. Python persistence remains not implemented and not supported.
- `redact_secret_vault.persistent.store_memory` ([#124](https://github.com/redact-secret/redact-secret-vault/issues/124)): `create_memory_store`, a volatile reference `Store` in process memory (standard library only; `cross_process=False`, `durability="volatile"`). Each operation's atomic section runs under a `threading.Lock` with no `await` inside, so it holds across threads and event loops, not by the GIL; a restart loses everything. It has no hold point and no fault hook: the Python schedule driver and the store-level mutation controls live in the test tree, outside the wheel. All 104 store-level cases of the [schedule corpus](conformance/persistent/v1/SCHEDULES.md) pass, none skipped (the 15 server-level cases are skipped with the reason that a store is not a server), and 22 stores each with one broken decision (stale commit and create reads, a missing revocation, generation, revision, budget, receipt, digest, epoch, or clock comparison, early sweeps, and others) fail the schedule that tests the decision. This is an in-memory store: it says nothing about a database adapter.
- `redact_secret_vault.persistent` ([#125](https://github.com/redact-secret/redact-secret-vault/issues/125)): `create_persistent_server_vault`, the persistent server profile in Python, over an injected `Store`, `RecordCrypto`, digest key, principal and session resolvers, restore policy, and lifecycle policy. Async only. Restore follows the order of specification section 7.2, with attempts, `resolve_attempt`, and `COMMIT_AMBIGUOUS`; `store.commit_restore` and `store.create_capture` run in an inner task under `asyncio.shield`, so a cancelled caller gets no field and the attempt is resolved later. Record time is wall time, floored and non-decreasing. `expected_pii_activation` is required, and a worker whose core disagrees fails `PII_ACTIVATION_MISMATCH` before it stores anything. Every `VaultServerError` it raises has no `__cause__` and no `__context__`. The capture logic of `InMemoryVaultServer` moved into `redact_secret_vault.capture_plan`, which both servers call; the in-memory server's behavior is unchanged (its tests and the shared corpus pass as before). `VaultServerErrorCode`, `ServerDenialReason`, `ServerAuditOperation`, `ServerAuditEvent`, and `VaultServerError` gain the persistent vocabulary (`UNSUPPORTED_STORE`, `STORE_UNAVAILABLE`, `STORE_QUARANTINED`, `COMMIT_AMBIGUOUS`, `RESTORE_CONFLICT`, `CLOCK_SKEW`, `LIFECYCLE_DENIED`, `KEY_UNAVAILABLE`, `CLOSED`; `integrity-failure`, `key-unavailable`, `attempt-mismatch`, `attempt-already-committed`; `capture`, `delete-ciphertext`, `resolve-attempt`; `capture_id`, `attempt_id`); the in-memory server uses none of them. All 15 server-level cases of the schedule corpus pass against the reference store and the crypto layer. The capture of every case of `conformance/v1/corpus.json`, in the PII-off and PII-on lanes, retains the same set, with equal stored values and types, as the in-memory server; the two documented differences are asserted. Leak tests cover errors, tracebacks and frame locals, logging, warnings, standard streams, and audit events over every negative path, a store that raises and one that lies, and key-provider failures; cancellation is tested at every `await` of capture and restore. This is the server logic over an in-memory store and a fake or real core: no durable backend, no interoperation with the JavaScript profile, and no bridge qualification.
- `redact_secret_vault.stores.postgres` ([#126](https://github.com/redact-secret/redact-secret-vault/issues/126)), behind the `postgres` extra: `create_postgres_store`, a ciphertext-only `Store` over `psycopg` 3 against the schema `@redact-secret/store-postgres` owns (Python creates no table and runs no migration), over a pool the application injects, with the lock order and conflict rule of specification section 5.2, fork detection, and every row value checked against the contract. Run against PostgreSQL 17.11 with `psycopg` 3.3.6 (`binary`): the schedule corpus through the Python driver, two-process cases with real processes, disconnects before and after `COMMIT`, malicious rows, and a leak test with logging at `DEBUG`. New CI job `python-postgres`. The extra names plain `psycopg`, which needs a system `libpq` to import; `psycopg[binary]` is the tested variant.
- `redact_secret_vault.keys.aws_kms` ([#127](https://github.com/redact-secret/redact-secret-vault/issues/127)), behind the `aws-kms` extra: `create_aws_kms_key_provider` over an injected `boto3` client, with the key reference, profile, and encryption context of `@redact-secret/key-provider-aws-kms`. Run against a real key in `us-east-1`: a data key wrapped by one language is unwrapped by the other. Measured: `botocore` at `DEBUG` writes the plaintext data key and the key ARN; do not enable it.
- `redact_secret_vault.keys.aws_kms` ([#145](https://github.com/redact-secret/redact-secret-vault/issues/145)): the provider fails closed while `DEBUG` is enabled for `botocore`, `botocore.parsers`, `botocore.hooks`, `botocore.endpoint`, `boto3`, or `urllib3.connectionpool`, because `botocore` writes the plaintext data key, the wrapped key, and the key ARN there. Construction raises `KEY_INVALID_ARGUMENT` and every KMS call raises `KEY_UNAVAILABLE` before the request; the new keyword `allow_sdk_debug_logging=True` opts out and is documented as writing key material to the application's logs. No logging configuration is changed. Verified on the real `boto3` with a stubbed HTTP layer. Python persistence is still not supported.
- `@redact-secret/key-provider-aws-kms` ([#145](https://github.com/redact-secret/redact-secret-vault/issues/145)): [finding](docs/research/aws-sdk-v3-logger-and-key-material.md) and a regression test. A `logger` in the AWS SDK v3 client configuration never receives the plaintext data key (`Plaintext` is marked sensitive); it does receive the key ARN, the wrapped key, and the context digest. No provider change.
- Qualification ([#128](https://github.com/redact-secret/redact-secret-vault/issues/128)): [`docs/research/qualification-python-persistence-0.1.0b3.md`](docs/research/qualification-python-persistence-0.1.0b3.md) lists gates G1 to G9 with the cells run, versions, and results, including what failed, what was skipped, and what was not run. The core bridge is not qualified ([decision](docs/decisions/limit-python-persistence-claim-to-a-supplied-core-client.md)). Not every gate is passed; Python persistence stays not supported.

### New packages at 0.1.0-alpha.1

**Release date: 2026-10-02.** Published by hand by the maintainer under the `alpha` dist-tag (the registry also set `latest`), without provenance; the `v0.1.0-beta.4` workflow skipped them. There is no `key-provider-local` package: the local key provider is the `@redact-secret/vault-crypto/local-key-provider` entry. Together they are the persistent profile of the [persistent vault specification](docs/specs/persistent-vault.md), decided in the [ciphertext-only store decision](docs/decisions/supersede-persistent-store-contract.md). What was tested, and on what, is in the [qualification record](docs/research/qualification-persistence-0.1.0-alpha.1.md); anything it does not name is unsupported.

- `@redact-secret/vault-contracts` 0.1.0-alpha.1 ([#104](https://github.com/redact-secret/redact-secret-vault/issues/104)): the `Store`, `KeyProvider`, and `RecordCrypto` types, `LIMITS`, the store input validators, and the fixed-message error classes `StoreError`, `KeyProviderError`, `RecordCryptoError`. No dependency, no I/O.
- `@redact-secret/vault-crypto` 0.1.0-alpha.1 ([#106](https://github.com/redact-secret/redact-secret-vault/issues/106), [#107](https://github.com/redact-secret/redact-secret-vault/issues/107)): record format version 1 over WebCrypto (canonical encoding, one data key per capture, an HKDF-derived AES-256-GCM key per entry), the request digest and session tag, and `createLocalKeyProvider` at `./local-key-provider` for key material the application injects. No default key and no key from the environment. Checked against the shared [test vectors](conformance/persistent/v1/README.md). The local provider is not qualified as a production key-management profile.
- `@redact-secret/vault-conformance` 0.1.0-alpha.1 ([#108](https://github.com/redact-secret/redact-secret-vault/issues/108), [#110](https://github.com/redact-secret/redact-secret-vault/issues/110)): `storeConformanceCases` and `keyProviderConformanceCases`, the `createFaultyStore` fault injector, a reference model, and `createInsecureTestKeyProvider`, which must never protect real data. A pass shows a correct adapter behaves for the inputs run; it does not make a hostile adapter safe.
- `@redact-secret/store-memory` 0.1.0-alpha.1 ([#108](https://github.com/redact-secret/redact-secret-vault/issues/108)): a ciphertext-only reference `Store` in process memory, for tests and development. **Non-durable and single-process; not persistence.** A persistent server refuses it unless the application passes `allowNonDurableStore: true`.
- `@redact-secret/store-postgres` 0.1.0-alpha.1 ([#20](https://github.com/redact-secret/redact-secret-vault/issues/20)): a ciphertext-only `Store` on PostgreSQL over a pool the application creates and closes (`pg` is a peer dependency). Qualified on PostgreSQL 17.11 with `pg` 8.23.1 and Node.js 22, as a single primary with `fsync` and `synchronous_commit` on, or a primary with one synchronous standby. Not qualified: any other PostgreSQL version, asynchronous replicas as failover targets, connection poolers, managed services, and TLS. See its [README](packages/store-postgres/README.md) and [report](packages/store-postgres/qualification/report/report.md).
- `@redact-secret/store-sqlite` 0.1.0-alpha.1 ([#130](https://github.com/redact-secret/redact-secret-vault/issues/130)): a ciphertext-only `Store` on one SQLite database file on a local file system, for processes of one host (the `sqlite-local-wal` profile of the [backend research](docs/research/persistent-backend-capabilities.md)). The package imports no driver: the application injects `better-sqlite3` (`^12.11.1`) or Node.js's `node:sqlite` through `betterSqlite3Driver` or `nodeSqliteDriver`, behind one thin interface and one common SQLite version check ([decision](docs/decisions/choose-sqlite-driver.md)). The base packages stay driver-free, and `better-sqlite3` is installed only by the `sqlite` CI job (`npm run install:sqlite-driver`): no workspace depends on it, it is absent from the root lockfile, and no other job's `npm ci` runs its install script. The store refuses to start unless SQLite is 3.51.3 or later (or carries the backported fix), `journal_mode=WAL` with `synchronous=FULL` (or `DELETE` with `EXTRA`) is in effect, and `busy_timeout` is finite; every mutation runs in `BEGIN IMMEDIATE`. `restoreDetection` is a counter high-water mark and a marker file, and it is shown **not** to notice a backup restored together with its marker file; the recovery runbook is the control. **Partial record, not a supported profile:** the shared conformance suite (zero unexplained skips), two server processes on one file, process kills around commit, and backup by the backup API, `VACUUM INTO`, and file copy ran on one machine (macOS arm64): over `better-sqlite3` 12.11.1 (SQLite 3.53.2) on Node.js 22.16.0, and over `node:sqlite` on Node.js 22.23.3, 24.21.0, and 25.9.0. **The power-loss simulation was not run**, nor Node.js 20 or Linux (a `sqlite` CI job is defined). See the [record](docs/research/qualification-store-sqlite-0.1.0-alpha.1.md) and the [reference](docs/reference/store-sqlite.md).
- `@redact-secret/key-provider-aws-kms` 0.1.0-alpha.1 ([#113](https://github.com/redact-secret/redact-secret-vault/issues/113)): an optional `KeyProvider` over a KMS client the application supplies (`@aws-sdk/client-kms` is a peer dependency). Run once against real AWS KMS in `us-east-1` with single-Region symmetric keys; multi-Region keys, custom key stores, and cross-account use are not tested. See its [README](packages/key-provider-aws-kms/README.md).

Known limits, stated in the [threat model](docs/specs/threat-model.md#persistent-mappings--implemented-on-main-qualified-for-two-postgresql-profiles): release is at most once, never exactly once; deleting ciphertext is not erasure; a party that can write the database can reset a use counter; two database restore methods are not detected by the PostgreSQL store, so the recovery runbook is required after every recovery.

- `redact-secret-vault` (Python): `NodeCoreBridge` reuses one long-lived Node.js bridge process per bridge instead of spawning one per scan ([#89](https://github.com/redact-secret/redact-secret-vault/issues/89)). One request is in flight per process, each response must echo its request id, and any failure (timeout, crash, malformed, oversized, or out-of-sequence output, core error, version or PII mismatch, interrupted call) retires the process; the next scan starts a fresh one whose PII activation is checked again. The bridge's stderr is discarded. Earlier inputs can now remain in the bridge's heap for up to the lifetime bounds; see the threat model's [Python core bridge](docs/specs/threat-model.md#python-core-bridge-redact-secret-vault--research-grade-not-qualified) section.

An internal expiry-ordered queue now visits only captures whose time has come; the cost is flat in retained entries. When and which entries are swept, the `>=` expiry boundary, limits accounting, audit events, and denials are unchanged.
- `@redact-secret/vault`: capture output is validated in a single pass ([#88](https://github.com/redact-secret/redact-secret-vault/issues/88)). The check that every issued token appears exactly once and nothing else token-like does now walks the output once instead of searching it per token (about 47 ms → 0.2 ms for 256 tokens in 1 MiB). It accepts exactly the outputs the old check did and still fails closed with `INVARIANT_VIOLATION` before commit. Most of the remaining capture cost on large, finding-dense inputs is inside the core's `redact` with a JavaScript placeholder formatter, tracked upstream in [redact-secret#997](https://github.com/redact-secret/redact-secret/issues/997).

Every call used to copy both tombstone maps, adding about 0.06 ms per 1000 recently revoked captures to each capture, restore, and revoke; the sweep now walks tombstones in time order and stops at the first live one. Revoking an already-remembered capture now refreshes its position so that order holds. Which revoked captures are remembered, and the `revoked` denial, are unchanged.

### Notes

- **`displayFormatter` must not reproduce any finding's text.** The core (beta.10) rejects a label that reproduces the matched text of any finding in the same input, including a sibling `warn` or `allow` finding. The capture fails with `CORE_FAILURE` / `coreCode: "INVALID_PLACEHOLDER"` and commits nothing ([#43](https://github.com/redact-secret/redact-secret-vault/issues/43)). Use fixed labels such as `[REDACTED]` or the finding type.
- **PII increases finding counts.** Every finding counts toward `maxFindings`, including PII that is not retained or is passed through, so enabling PII can push an input that fit before over the limit: `CORE_FAILURE` / `coreCode: "FINDING_LIMIT_EXCEEDED"`, nothing committed ([#43](https://github.com/redact-secret/redact-secret-vault/issues/43)).
- **Medium- and Low-confidence PII fails `UNREDACTED_FINDINGS` by default.** Those findings default to the core's `warn` action. For example, beta.10 rates a labeled seven-digit local phone number as Medium `pii_global_phone`. Map the types to `redact` with a core `policy`, or choose `unredacted: "pass-through"` knowingly. `pii.retain` applies only to `redact` findings.
- **Worker mode cannot pass `policy` or `eligible`.** A Worker capture containing warn-level PII can only reject (`UNREDACTED_FINDINGS`) or use `unredacted: "pass-through"`.
- **A typed label is not a restore capability.** A core typed placeholder for a PII type (for example `<PII_JURISDICTION_US_SSN_1>`) grants nothing and does not imply retention; restoration requires an issued `<rsv_…>` token, a sink/path grant, and, for PII, the exact-type allowlist ([decision note](docs/decisions/decouple-typed-placeholders-from-restoration.md)).
- On a core without PII support (beta.9), callers that pass no PII option see no behavior change. Any PII option fails closed with `PII_UNAVAILABLE`, and `pii: []` equals omission. (The supported, pinned core is beta.10.)
