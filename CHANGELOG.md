## Unreleased

### @redact-secret/vault 0.1.0-beta.4, @redact-secret/vault-server 0.1.0-beta.4

**Not released.** These versions are on `main` only; npm's `beta` and `latest` still name `0.1.0-beta.3`. `@redact-secret/core` peer stays `0.1.0-beta.12` exactly; `@redact-secret/vault-server` depends on `@redact-secret/vault` `0.1.0-beta.4` exactly. `redact-secret-vault` (Python) is unchanged at `0.1.0b3`. No performance figures: nothing was measured for these changes. The release date, tag, run, and provenance are recorded here when the release happens.

- `@redact-secret/vault`: internal capture-plan entry ([#109](https://github.com/redact-secret/redact-secret-vault/issues/109)). Everything a capture decides before it retains anything (argument validation, the core scan, the action gate, the PII allowlist, `eligible`, limits, token issuance, formatting, and output validation) moves into one module that the in-memory vault and `@redact-secret/vault-server` both call. It is exported as `@redact-secret/vault/internal/capture-plan` under the `node` condition only, is not re-exported from the package root or the Worker entry points, and is not a supported API: it can change in any release. **No public API change**: `.`, `./worker`, and `./worker/host` export what they did, and capture behavior is unchanged.
- `@redact-secret/vault-server`: new opt-in entry `@redact-secret/vault-server/persistent` ([#109](https://github.com/redact-secret/redact-secret-vault/issues/109)) with `createPersistentServerVault`: `capture`, `restore`, `revoke`, `deleteCaptureCiphertext`, `resolveAttempt`, and `close` over an injected `Store` and `RecordCrypto`, with a required `lifecyclePolicy`, `digestKey`, and `recoveryEpoch`. See the [package README](packages/vault-server/README.md#persistent-profile) and the [persistent vault specification](docs/specs/persistent-vault.md) §8. Alpha; qualified only as the [qualification record](docs/research/qualification-persistence-0.1.0-alpha.1.md) states. `createServerVault` and the default entry behave as before, and the default entry loads none of the persistent code.
- `@redact-secret/vault-server`: **the shared types gain members.** Code with an exhaustive `switch` over one of these types needs new cases (or a default) to keep compiling, even if it never uses the persistent profile:
  - `ServerVaultErrorCode`: `UNSUPPORTED_STORE`, `STORE_UNAVAILABLE`, `STORE_QUARANTINED`, `COMMIT_AMBIGUOUS`, `RESTORE_CONFLICT`, `CLOCK_SKEW`, `LIMIT_EXCEEDED`, `LIFECYCLE_DENIED`, `KEY_UNAVAILABLE`, `CLOSED`. Only the persistent profile throws them.
  - `ServerDenialReason`: `integrity-failure`, `key-unavailable`, `attempt-mismatch`, `attempt-already-committed`. Only the persistent profile reports them.
  - `ServerAuditOperation`: `capture`, `delete-ciphertext`, `resolve-attempt`. `ServerAuditEvent` gains optional `captureId` and `attemptId`, and `VaultServerError` gains `attemptId` (set only for `COMMIT_AMBIGUOUS`).
- `@redact-secret/vault-server`: new runtime dependency `@redact-secret/vault-contracts` `0.1.0-alpha.1`, pinned exactly. It has no dependency of its own and is imported only by the persistent entry. The package still names no database driver, key-service SDK, or cipher.
- Release automation ([#112](https://github.com/redact-secret/redact-secret-vault/issues/112)): `release.yml` runs the persistence tests, the packed-artifact boundary check, the clean-consumer check, and `store-postgres` against PostgreSQL 17 before publishing, and publishes the new packages in dependency order through `scripts/publish-workspace.mjs`. See [RELEASING.md](RELEASING.md#persistence-packages).

### Developer experience

**Not released.** On `main` only.

- `@redact-secret/vault`, `@redact-secret/vault-server`: the error for an uninitialized core names the fix ([#133](https://github.com/redact-secret/redact-secret-vault/issues/133)). `CORE_FAILURE` with `coreCode: "NOT_INITIALIZED"` (and the server's `VAULT_FAILURE` wrapping it) now has its own fixed message: pass `pii: []`, or await the core's `initialize()` first. Codes are unchanged, and every other core failure keeps the generic message. Omitting `pii` still does not initialize the core. Code that compares `error.message` for this case needs the new text; compare `code` and `coreCode` instead.
- `@redact-secret/vault-server`: new opt-in entry `@redact-secret/vault-server/policies` ([#134](https://github.com/redact-secret/redact-secret-vault/issues/134)) with `denyByDefault`, `allowSameTenantOnly`, `allowSinkPurposes(table)`, and `allOf(...policies)`. They are ordinary `ServerReleasePolicy` values, evaluated after the server's own checks. `allOf` hands back any decision that is not exactly `{ allow: true }`, so a malformed decision is still `policy-evaluation-error`, and an empty `allOf()` denies. The [decision record](docs/decisions/define-server-authority-interface.md#reference-policy-examples) has an addendum.
- `redact-secret-vault` (Python): `python -m redact_secret_vault doctor [--node-modules PATH]` ([#135](https://github.com/redact-secret/redact-secret-vault/issues/135)) checks the `node` executable, where the core is loaded from, that it loads, and that it is the pinned version, and prints a fix for each failure. It exits 1 if a check fails and prints no finding value. The version is still `0.1.0b3`; this is not on PyPI.
- [`examples/`](examples/README.md) ([#136](https://github.com/redact-secret/redact-secret-vault/issues/136)): five programs that run as they are (single user, multi-turn, denied restore, a server with two tenants, Python). `npm run examples` runs them, and CI does on every push.
- [`examples/persistent/`](examples/persistent/README.md) ([#137](https://github.com/redact-secret/redact-secret-vault/issues/137)): a Docker Compose file, an idempotent setup script, and a two-process demo for the persistent profile. Development only; not a qualified deployment profile.
- Release automation ([#138](https://github.com/redact-secret/redact-secret-vault/issues/138)): `release.yml` pins the links of every package README to the release tag before publishing, and turns relative links into absolute ones ([RELEASING.md](RELEASING.md#readme-links)). Package manifests are unchanged.

Detail moved, unchanged, to [`docs/guides/`](docs/README.md) and `docs/reference/`; release tables moved to [`docs/status.md`](docs/status.md). New: [troubleshooting](docs/guides/troubleshooting.md). ### New packages at 0.1.0-alpha.1

**Not released.** None of these names exists on npm yet. Each will publish under the `alpha` dist-tag. Together they are the persistent profile of the [persistent vault specification](docs/specs/persistent-vault.md), decided in the [ciphertext-only store decision](docs/decisions/supersede-persistent-store-contract.md). What was tested, and on what, is in the [qualification record](docs/research/qualification-persistence-0.1.0-alpha.1.md); anything it does not name is unsupported.

- `@redact-secret/vault-contracts` 0.1.0-alpha.1 ([#104](https://github.com/redact-secret/redact-secret-vault/issues/104)): the `Store`, `KeyProvider`, and `RecordCrypto` types, `LIMITS`, the store input validators, and the fixed-message error classes `StoreError`, `KeyProviderError`, `RecordCryptoError`. No dependency, no I/O.
- `@redact-secret/vault-crypto` 0.1.0-alpha.1 ([#106](https://github.com/redact-secret/redact-secret-vault/issues/106), [#107](https://github.com/redact-secret/redact-secret-vault/issues/107)): record format version 1 over WebCrypto (canonical encoding, one data key per capture, an HKDF-derived AES-256-GCM key per entry), the request digest and session tag, and `createLocalKeyProvider` at `./local-key-provider` for key material the application injects. No default key and no key from the environment. Checked against the shared [test vectors](conformance/persistent/v1/README.md). The local provider is not qualified as a production key-management profile.
- `@redact-secret/vault-conformance` 0.1.0-alpha.1 ([#108](https://github.com/redact-secret/redact-secret-vault/issues/108), [#110](https://github.com/redact-secret/redact-secret-vault/issues/110)): `storeConformanceCases` and `keyProviderConformanceCases`, the `createFaultyStore` fault injector, a reference model, and `createInsecureTestKeyProvider`, which must never protect real data. A pass shows a correct adapter behaves for the inputs run; it does not make a hostile adapter safe.
- `@redact-secret/store-memory` 0.1.0-alpha.1 ([#108](https://github.com/redact-secret/redact-secret-vault/issues/108)): a ciphertext-only reference `Store` in process memory, for tests and development. **Non-durable and single-process; not persistence.** A persistent server refuses it unless the application passes `allowNonDurableStore: true`.
- `@redact-secret/store-postgres` 0.1.0-alpha.1 ([#20](https://github.com/redact-secret/redact-secret-vault/issues/20)): a ciphertext-only `Store` on PostgreSQL over a pool the application creates and closes (`pg` is a peer dependency). Qualified on PostgreSQL 17.11 with `pg` 8.23.1 and Node.js 22, as a single primary with `fsync` and `synchronous_commit` on, or a primary with one synchronous standby. Not qualified: any other PostgreSQL version, asynchronous replicas as failover targets, connection poolers, managed services, and TLS. See its [README](packages/store-postgres/README.md) and [report](packages/store-postgres/qualification/report/report.md).
- `@redact-secret/key-provider-aws-kms` 0.1.0-alpha.1 ([#113](https://github.com/redact-secret/redact-secret-vault/issues/113)): an optional `KeyProvider` over a KMS client the application supplies (`@aws-sdk/client-kms` is a peer dependency). Run once against real AWS KMS in `us-east-1` with single-Region symmetric keys; multi-Region keys, custom key stores, and cross-account use are not tested. See its [README](packages/key-provider-aws-kms/README.md).

Known limits, stated in the [threat model](docs/specs/threat-model.md#persistent-mappings--implemented-on-main-qualified-for-two-postgresql-profiles): release is at most once, never exactly once; deleting ciphertext is not erasure; a party that can write the database can reset a use counter; two database restore methods are not detected by the PostgreSQL store, so the recovery runbook is required after every recovery.

## @redact-secret/vault 0.1.0-beta.1, @redact-secret/vault-server 0.1.0-beta.1, redact-secret-vault 0.1.0b1 (Python)

**Release date: 2026-09-29.** First beta line; npm dist-tag `beta` (`publishConfig.tag` moves from `alpha`). `@redact-secret/core` peer stays `0.1.0-beta.10` exactly; `@redact-secret/vault-server` depends on `@redact-secret/vault` `0.1.0-beta.1` exactly. No breaking change from `0.1.0-alpha.3` / `0.1.0a3`; the changes below are performance and Python bridge lifecycle work. Performance against `0.1.0-alpha.3` (`corpus-v1`, `standard` tier, `github-actions/Linux/X64/ubuntu24/20260920.314.1`, PII off and on): 0 warn, 0 fail; see [docs/research/perf/0.1.0-beta.1.json](docs/research/perf/0.1.0-beta.1.json).

- `redact-secret-vault` (Python): `NodeCoreBridge` reuses one long-lived Node.js bridge process per bridge instead of spawning one per scan ([#89](https://github.com/redact-secret/redact-secret-vault/issues/89)). A capture was dominated by process start (about 250× the JS cost); the bridge now starts once (about 30 ms) and each scan is a framed request/response on stdin/stdout (Python/JS capture about 4×). One request is in flight per process, each response must echo its request id, and any failure (timeout, crash, malformed, oversized, or out-of-sequence output, core error, version or PII mismatch, interrupted call) retires the process; the next scan starts a fresh one whose PII activation is checked again. New: `close()` and context-manager support; lifetime bounds `max_scans_per_process` (default 10 000), `max_process_age_s` (600), and `idle_timeout_s` (60); `timeout_s` is validated at construction (`INVALID_ARGUMENT`); requests over 448 MiB raise `LIMIT_EXCEEDED`; a scan after `close()` raises `CORE_FAILURE` / `BRIDGE_CLOSED`. The bridge's stderr is discarded. Earlier inputs can now remain in the bridge's heap for up to the lifetime bounds; see the threat model's [Python core bridge](docs/specs/threat-model.md#python-core-bridge-redact-secret-vault--research-grade-not-qualified) section.
- `@redact-secret/vault`: expired entries are swept without copying the entry map ([#86](https://github.com/redact-secret/redact-secret-vault/issues/86)). `#sweep` used to copy and walk every retained entry on each capture, restore, and `stats()`, so per-call cost grew with the vault's size (about 4.4 ms of capture overhead and 6.5 ms per restore at 100 000 entries). An internal expiry-ordered queue now visits only captures whose time has come; the cost is flat in retained entries. When and which entries are swept, the `>=` expiry boundary, limits accounting, audit events, and denials are unchanged.
- `@redact-secret/vault`: capture output is validated in a single pass ([#88](https://github.com/redact-secret/redact-secret-vault/issues/88)). The check that every issued token appears exactly once and nothing else token-like does now walks the output once instead of searching it per token (about 47 ms → 0.2 ms for 256 tokens in 1 MiB). It accepts exactly the outputs the old check did and still fails closed with `INVARIANT_VIOLATION` before commit. Most of the remaining capture cost on large, finding-dense inputs is inside the core's `redact` with a JavaScript placeholder formatter, tracked upstream in [redact-secret#997](https://github.com/redact-secret/redact-secret/issues/997).
- `@redact-secret/vault-server`: revocation tombstones are swept incrementally ([#87](https://github.com/redact-secret/redact-secret-vault/issues/87)). Every call used to copy both tombstone maps, adding about 0.06 ms per 1000 recently revoked captures to each capture, restore, and revoke; the sweep now walks tombstones in time order and stops at the first live one. Revoking an already-remembered capture now refreshes its position so that order holds. Which revoked captures are remembered, and the `revoked` denial, are unchanged.
- Performance measurement ([#74](https://github.com/redact-secret/redact-secret-vault/issues/74)): a `bench/` harness compares a candidate against the previous published version (`npm run bench:compare`), and `.github/workflows/bench.yml` runs it on release tags. See [docs/research/perf](docs/research/perf/README.md) and [RELEASING.md](RELEASING.md#performance-check). Relative Markdown links are now checked in CI (`npm run check:links`, [#90](https://github.com/redact-secret/redact-secret-vault/issues/90)).
- `redact-secret-vault` `0.1.0a3` (Python): first publish to PyPI. `release.yml` now tests the package on Python 3.12, builds the sdist and wheel (checking that the wheel carries `boundary/core_bridge.mjs` and that both carry the `pyproject.toml` version), and uploads them with `pypa/gh-action-pypi-publish` through PyPI trusted publishing (OIDC, no API token) with PEP 740 attestations. The upload is skipped when that version is already on PyPI, like the npm steps. The npm jobs are unchanged. The version moves from `0.1.0a2`, which was never published, to `0.1.0a3`. See [RELEASING.md](RELEASING.md#python).
- `redact-secret-vault` `0.1.0a3` (Python): application-owned core location. A `pip`-installed package keeps `boundary/core_bridge.mjs` in site-packages, where Node.js cannot resolve `@redact-secret/core` unless the virtualenv sits inside the project that installed it; before this change such a `NodeCoreBridge` failed every scan with `CORE_FAILURE` / `BRIDGE_PROCESS_FAILED`. `NodeCoreBridge(node_modules=...)` and, when that is `None`, the `REDACT_SECRET_VAULT_NODE_MODULES` environment variable name the `node_modules` directory to load the core from. The bridge reads `<node_modules>/@redact-secret/core/package.json`, resolves its `exports` entry, and imports that file, never searching parent directories or the working directory. A missing or unusable directory raises `CORE_FAILURE` with `core_code` `BRIDGE_CORE_NOT_FOUND` (`BRIDGE_CORE_LOAD_FAILED` if the core fails to load), without the path. Without either setting the script-relative resolution is unchanged, except that a core it cannot find now reports `BRIDGE_CORE_NOT_FOUND` instead of `BRIDGE_PROCESS_FAILED`. The pinned core version check is unchanged. `release.yml` now installs the built wheel into a virtualenv outside the repository and scans a synthetic token through `node_modules=` before anything is uploaded.

## @redact-secret/vault 0.1.0-alpha.3, @redact-secret/vault-server 0.1.0-alpha.3

**Release date: 2026-09-28.** Both packages are published from `release.yml` through npm trusted publishing with provenance. `@redact-secret/core` peer stays `0.1.0-beta.10` exactly; `@redact-secret/vault-server` depends on `@redact-secret/vault` `0.1.0-alpha.3` exactly. No breaking change from `0.1.0-alpha.2`. The Python package (`redact-secret-vault` `0.1.0a2`) is not published.

- `@redact-secret/vault` Worker mode: the Worker script can own a core policy ([#59](https://github.com/redact-secret/redact-secret-vault/issues/59)). `startVaultWorkerHost({ policy })` takes a core `SecretPolicy` and applies it to every capture in that Worker, with the main-thread `policy` semantics. Worker captures containing warn-level PII can now be redacted instead of rejected or passed through. The page still cannot send, see, or replace a policy: capture options, `vault-ready`, and the protocol version (`2`) are unchanged. PII retention is unchanged: a PII finding escalated to `redact` is not restorable unless `pii.retain` names its type. An invalid `policy` (not an object with a callable `evaluate`) fails init with `INVALID_ARGUMENT` before the Worker's core is initialized. A policy that throws or returns an unknown action fails that capture as on the main thread (`CORE_FAILURE` / `POLICY_FAILURE` or `INVALID_POLICY_ACTION`), with nothing committed. Audit events do not report which findings a policy changed; the vault does not re-scan to find out. Recorded as an addendum to the [PII retention and activation decision](docs/decisions/decide-pii-retention-and-activation-ownership.md#addendum-2026-09-28-worker-script-owned-core-policy-59). Tested against a fake core and core `0.1.0-beta.10` (PII on) in Node.js, and in real dedicated Workers in Chromium, Firefox, and WebKit.
- Python distribution renamed ([#56](https://github.com/redact-secret/redact-secret-vault/issues/56)) before its first publish: `redact-secret-vault-server` → `redact-secret-vault`, import package `redact_secret_vault_server` → `redact_secret_vault`, directory `packages/vault-server-py` → `packages/vault-py`. The old name was never uploaded to PyPI. Version stays `0.1.0a2`; no behavior changed. Code importing `redact_secret_vault_server` must switch to `redact_secret_vault`. The rationale is a dated note on the [naming decision](docs/decisions/name-vault-packages-and-language-contract.md); intended PyPI trusted publishing is documented in [RELEASING.md](RELEASING.md#python), with no publish workflow yet.
- Release automation ([#55](https://github.com/redact-secret/redact-secret-vault/issues/55)): `release.yml` now tests and publishes `@redact-secret/vault-server` after `@redact-secret/vault` from the same tag, through npm trusted publishing with `--provenance`, with the same already-published and non-`latest` dist-tag guards. No package code changed.

### Breaking and behavior changes

- **Exact core peer `0.1.0-beta.10`** ([#41](https://github.com/redact-secret/redact-secret-vault/issues/41)). `@redact-secret/vault` and `@redact-secret/vault-server` peer-depend on `@redact-secret/core` `0.1.0-beta.10` exactly, `@redact-secret/vault-server` depends on `@redact-secret/vault` `0.1.0-alpha.2` exactly, and the Python bridge's `PINNED_CORE_VERSION` is `0.1.0-beta.10`. `@redact-secret/vault@0.1.0-alpha.1` remains the release for core `0.1.0-beta.9`. Install exact versions: `@redact-secret/vault`'s npm `latest` tag still points at `0.1.0-alpha.1`, and that version conflicts with core beta.10.
- **`NOT_INITIALIZED` when `pii` is omitted and the core is uninitialized** ([#38](https://github.com/redact-secret/redact-secret-vault/issues/38), [#41](https://github.com/redact-secret/redact-secret-vault/issues/41)). On beta.10, `createVault()` and `startVaultWorkerHost()` without `pii` no longer initialize the core. They adopt the activation the application already set, and fail with `CORE_FAILURE` / `coreCode: "NOT_INITIALIZED"` when nothing initialized it (in Worker mode, `createWorkerVault` rejects with that code). `createServerVault()` without `pii` fails the same way, as `VAULT_FAILURE` / `vaultCode: "CORE_FAILURE"` / `coreCode: "NOT_INITIALIZED"`. The vault no longer silently locks the realm's PII selection off.
  - **Migration:** pass `createVault({ pii: [] })` for PII off (likewise `startVaultWorkerHost({ pii: [] })` and `createServerVault({ ..., pii: [] })`), or await the core's own `initialize(...)` before creating the vault and keep omitting `pii`.
  - The Python `NodeCoreBridge` is unaffected: it initializes its own bridge process, with `pii=[]` by default.
- **Worker protocol version 2** ([#39](https://github.com/redact-secret/redact-secret-vault/issues/39)). The page client and the Worker host must come from the same release. A version-1 peer is rejected with `WORKER_PROTOCOL_VIOLATION`.

### Added

- `@redact-secret/vault`: `VaultOptions.pii` (forwarded as given to the core's `initialize({ pii })`; `[]` means PII off) and `VaultOptions.expectPiiActivation`. `Vault.piiActivation` reports the observed activation identity, or `null` on a core without PII support. PII support is detected at runtime from the core's `piiActivation` export, never by version.
- `@redact-secret/vault`: `CaptureOptions.pii: { retain }`, an exact-type allowlist. A `redact` finding whose type starts `pii_` is never retained unless its type is listed; otherwise it is replaced by a display placeholder that cannot be restored and counted in `unrestorable`. `eligible` can narrow the allowlist but cannot widen it.
- `@redact-secret/vault`: error codes `PII_UNAVAILABLE` (a PII option on a core without PII support, or capture retention while PII detection is off) and `PII_ACTIVATION_MISMATCH`. Core selector and activation failures surface as `CORE_FAILURE` with `coreCode` `PII_ACTIVATION_CONFLICT`, `PII_SELECTOR_INVALID`, `PII_SELECTOR_UNSUPPORTED`, or `PII_SELECTOR_UNAVAILABLE`.
- `@redact-secret/vault` Worker mode ([#39](https://github.com/redact-secret/redact-secret-vault/issues/39)): `startVaultWorkerHost({ pii, expectPiiActivation })` activates or adopts inside the Worker realm; `vault-ready` and `WorkerVault.piiActivation` report the observed identity; `createWorkerVault(worker, { expectPiiActivation })` rejects with `PII_ACTIVATION_MISMATCH`; Worker `capture` accepts `pii: { retain }`, validated on both sides. No page message can carry PII selectors. `VaultError` is now exported from `@redact-secret/vault/worker`, as the README already documented.
- `@redact-secret/vault-server` ([#38](https://github.com/redact-secret/redact-secret-vault/issues/38)): forwards `pii`, `expectPiiActivation`, and capture `pii` to the vault. Adds `ServerVault.piiActivation` and `VaultServerError.coreCode` (the core's code behind a `VAULT_FAILURE` / `CORE_FAILURE`).
- `redact-secret-vault-server` (Python, [#40](https://github.com/redact-secret/redact-secret-vault/issues/40)): `NodeCoreBridge(pii=..., expected_pii_activation=...)` forwards the selection to the core's `initialize({ pii })` in each bridge process, reports `CoreScanOutcome.pii_activation` (`None` without PII support), and pins the identity across scans (`PII_ACTIVATION_MISMATCH`). `CaptureOptions.pii=PiiRetention(retain=...)` follows the same allowlist rules, with error codes `PII_UNAVAILABLE` and `PII_ACTIVATION_MISMATCH`. Bridge responses are now parsed strictly.
- Qualification ([#42](https://github.com/redact-secret/redact-secret-vault/issues/42), [#43](https://github.com/redact-secret/redact-secret-vault/issues/43)): every runtime runs the suite with PII off and on, plus activation and retention scenarios in fresh realms. Conformance corpus 1.3.0 targets beta.10: 1.2.0 added 11 synthetic PII cases and 1.3.0 a default-confidence `warn` PII case, replayed by both the JavaScript and Python runners.

### Notes

- **`displayFormatter` must not reproduce any finding's text.** The core (beta.10) rejects a label that reproduces the matched text of any finding in the same input, including a sibling `warn` or `allow` finding. The capture fails with `CORE_FAILURE` / `coreCode: "INVALID_PLACEHOLDER"` and commits nothing ([#43](https://github.com/redact-secret/redact-secret-vault/issues/43)). Use fixed labels such as `[REDACTED]` or the finding type.
- **PII increases finding counts.** Every finding counts toward `maxFindings`, including PII that is not retained or is passed through, so enabling PII can push an input that fit before over the limit: `CORE_FAILURE` / `coreCode: "FINDING_LIMIT_EXCEEDED"`, nothing committed ([#43](https://github.com/redact-secret/redact-secret-vault/issues/43)).
- **Medium- and Low-confidence PII fails `UNREDACTED_FINDINGS` by default.** Those findings default to the core's `warn` action. For example, beta.10 rates a labeled seven-digit local phone number as Medium `pii_global_phone`. Map the types to `redact` with a core `policy`, or choose `unredacted: "pass-through"` knowingly. `pii.retain` applies only to `redact` findings.
- **Worker mode cannot pass `policy` or `eligible`.** A Worker capture containing warn-level PII can only reject (`UNREDACTED_FINDINGS`) or use `unredacted: "pass-through"`.
- **A typed label is not a restore capability.** A core typed placeholder for a PII type (for example `<PII_JURISDICTION_US_SSN_1>`) grants nothing and does not imply retention; restoration requires an issued `<rsv_…>` token, a sink/path grant, and, for PII, the exact-type allowlist ([decision note](docs/decisions/decouple-typed-placeholders-from-restoration.md)).
- On a core without PII support (beta.9), callers that pass no PII option see no behavior change. Any PII option fails closed with `PII_UNAVAILABLE`, and `pii: []` equals omission. (The supported, pinned core is beta.10.)

## @redact-secret/vault 0.1.0-alpha.1

First alpha. In-memory, whole-input capture and structured-field restoration for Node.js and browser main-thread runtimes, against `@redact-secret/core@0.1.0-beta.9` exactly.

- `createVault` with bounded entries, retained bytes, value size, input size, findings, entry TTL, vault lifetime, and restore size.
- `capture` gates on core actions (`block` aborts, `warn`/`allow` rejected unless `unredacted: "pass-through"`), issues 128-bit `<rsv_…>` tokens, refuses token-like input literals, and commits only after output validation.
- `restore` into application-granted `sink` + exact `path` pairs, with whole-request preflight, per-entry use budgets (default 1), a page-local `releasePolicy`, and fail-closed handling of altered tokens.
- `revoke`, `dispose`, `stats`, sanitized `VaultError` codes, and safe-metadata audit events.
- Not included: Worker mode, server authorization, persistence, streaming, and free-text restore.
