# Decide the Python persistence API shape, packaging, and version floor

> **Python persistence is not implemented and not supported.** This record fixes how the groundwork issues [#119](https://github.com/redact-secret/redact-secret-vault/issues/119) to [#122](https://github.com/redact-secret/redact-secret-vault/issues/122) are built. It claims nothing about a store, a server profile, or a qualification; those stay with the [plan](../plans/python-persistence-parity.md) and its later issues, and support is stated only by the qualification record of issue [#128](https://github.com/redact-secret/redact-secret-vault/issues/128).

## Context

The plan's [section 9](../plans/python-persistence-parity.md#9-open-questions) left several questions open that the first four handoffs cannot avoid. Each is answered with the recommendation the plan already gives. Where a later measurement can change an answer, the record says what would change it.

## Decisions

1. **One distribution with extras** (plan section 4.1, question 2). `redact-secret-vault` stays the only Python distribution. The base wheel has no `Requires-Dist` without an `extra ==` marker. The extras are `crypto` (`cryptography>=47`), `postgres` (`psycopg>=3.2,<4`), and `aws-kms` (`boto3>=1.43`). Per-module support status is stated in documentation, not by version number. A module moves to its own distribution only when it needs a different release cadence or a second backend of its kind exists, and that would need a new naming decision.
2. **Async-only persistent API** (plan section 3.7, question 1). `Store`, `KeyProvider`, and `RecordCrypto` are `typing.Protocol` classes with `async def` methods. There is no synchronous twin. Pure functions (validators, canonical encoders, digests) are synchronous. A WSGI deployment calls the async API through one long-lived event-loop thread per process.
3. **Python 3.11 floor for the persistent modules** (plan section 6.7, question 3). `requires-python` stays `>=3.10` because the in-memory server keeps its floor. Importing `redact_secret_vault.persistent` on 3.10 raises `ImportError`, and the tests of those modules are not collected on 3.10. 3.11 provides `asyncio.timeout` and exception notes, and 3.10 is at or past the end of its upstream support window.
4. **A bytes-only local key provider has its own profile name** (plan section 3.9, question 6). JavaScript accepts a non-extractable `CryptoKey` for local key material and Python has only bytes in process memory. The Python provider reports the profile `local-bytes-hkdf-aes-256-gcm-v1`, not `local-hkdf-aes-256-gcm-v1`, so a record or a qualification note cannot read as if the stronger handling had been used. The wrapped-key layout is the same, so the two interoperate on bytes.
5. **`KEY_ABORTED` is reserved** (question 8). Python signatures carry no abort signal. A provider raises `KEY_ABORTED` only for a cancellation it started itself. Task cancellation propagates as `asyncio.CancelledError` and is never converted. The local provider never raises it.
6. **The in-memory server is unchanged** (question 7). Its four `raise ... from exc` sites and its code-point identifier limit stay as published. The persistent modules follow the stricter rules (no `__cause__`, no `__context__`, UTF-16 lengths) and do not change the behavior of existing code.
7. **No thread offloading in the crypto layer** (plan section 3.7, issue [#122](https://github.com/redact-secret/redact-secret-vault/issues/122)). `RecordCrypto` runs HKDF and AES-256-GCM inline in the calling task. See the measurement below. A worker thread cannot be cancelled: `asyncio.to_thread` leaves the thread running after its task is cancelled, so the data key, entry keys, and decrypted payload it holds could not be overwritten on the cancellation path that spec section 7.6 and plan section 3.7 require. The work is also bounded by the store's `max_create_entries` and `max_create_bytes`.
8. **Deterministic test provider lives in the test tree.** It is not in the wheel, and it refuses to construct without the acknowledgement string `test-only`, as in JavaScript.
9. **The reference store has no hold point and no fault hook** ([#124](https://github.com/redact-secret/redact-secret-vault/issues/124)). `redact_secret_vault.persistent.store_memory` is plain code: the only seams are small protected decision methods (who is revoked, who is serving, the verdict of a commit, what a sweep may remove), and a test breaks one by subclassing. The hold point `before-commit`, the fault points, and the schedule driver live in the test tree (`packages/vault-py/tests/schedule_store.py`, `schedule_driver.py`, `store_mutants.py`), so no hook is in the wheel, which `scripts/verify-python-dist.py` already keeps free of test files. The store's atomic sections are guarded by a `threading.Lock`, not by the GIL.
10. **The Python persistent server profile** ([#125](https://github.com/redact-secret/redact-secret-vault/issues/125)). Where it follows the JavaScript profile it follows the specification; these are the choices Python forced or the plan fixed:
    - The operations are `def` methods that return the coroutine of one private wrapper, so the traceback of an error a caller receives starts in that wrapper's frame and no public frame holding a request survives. A `VaultServerError` is always built after the `except` block that classified the failure has ended.
    - Capture goes through `redact_secret_vault.capture_plan`, extracted from `InMemoryVaultServer._capture`; both servers call it. The core scan is blocking, so the persistent server runs it with `asyncio.to_thread`. A thread cannot be cancelled: a call cancelled during the scan leaves the scan to finish, and its result is dropped. The plan's errors keep the in-memory codes (`BLOCKED_FINDING`, `LIMIT_EXCEEDED`, and so on) and are not wrapped in a `VAULT_FAILURE` as in JavaScript.
    - `expected_pii_activation` is required (the bridge's own is optional). The server scans the empty string when it is created, compares the identity the core reports, and compares it again on every capture.
    - `store.commit_restore` and `store.create_capture` run in an inner task under `asyncio.shield`. When the caller is cancelled the inner call finishes under the store deadline and a capture the cancelled call may have created is fenced once. `CancelledError`, `KeyboardInterrupt`, and `SystemExit` are never converted.
    - Limits bound one capture, not a process: `max_entries` and `max_retained_bytes` count the capture alone, where the in-memory server counts what it already holds plus the capture. A clock reading below zero is `INVALID_ARGUMENT`, which the in-memory server accepts. Both differences are asserted in `tests/test_persistent_server_parity.py`.
11. **The Python PostgreSQL adapter** ([#126](https://github.com/redact-secret/redact-secret-vault/issues/126)). `redact_secret_vault.stores.postgres` runs the SQL of `packages/store-postgres/src/store.ts` against the tables that package owns. Python creates no table and runs no migration: the schema is applied by that package's `migrate` and `grantStatements`, and `tests/pg_prepare.mjs` applies it for the tests. The choices Python forced:
    - **Injected pool.** The application passes an object whose `connection()` returns an async context manager yielding a `psycopg.AsyncConnection` (`psycopg_pool.AsyncConnectionPool` is one; `psycopg-pool` is not a dependency of the extra). A connection whose state the adapter cannot vouch for (a failed `COMMIT` or `ROLLBACK`, a cancelled statement) is closed before it is handed back, so a pool discards it. The adapter works on a connection in either `autocommit` mode: it issues `SET TRANSACTION` after psycopg's own `BEGIN`, or `BEGIN` itself on an autocommit connection.
    - **`COMMIT` is a statement the adapter sends itself** and reads the command tag of, as the JavaScript adapter does with `pg`. A transport failure of that statement is `STORE_AMBIGUOUS` and the connection is discarded; a tag other than `COMMIT` (PostgreSQL answers a failed transaction with `ROLLBACK`) and a `COMMIT` that completed with a server warning are treated as not confirmed.
    - **Cancellation** is never converted. A `CancelledError` (or an interrupt) inside a transaction closes the connection and propagates; whether a `COMMIT` that was already on the wire took effect is then resolved through `inspect_attempt`, as after `STORE_AMBIGUOUS`.
    - **Fork.** A store records `os.getpid()` when it is created and raises `STORE_CLOSED` from any other process.
    - **Rows are data from a database the adapter does not control.** Every integer is checked `type(x) is int` and within `0 .. 2^53 - 1` (a `bigint` can hold more), every byte field is checked for type and length against the contract's limits, and every identifier against its pattern; anything outside is `STORE_UNAVAILABLE` and no row value is returned or named in an error. `read_entries` and `read_captures` return results in the order asked, as `store_memory` does; the JavaScript adapter returns identifier order.
    - **No hook in the wheel.** The adapter's one test seam is the class attribute `_NOW_SQL` (the SQL expression of the store clock), replaced by a test subclass so the time-dependent schedule cases run against real transactions. The hold point `before-commit` and the faults live in the test tree (`tests/pg_support.py`): the test pool wraps the connection and pauses or fails a `COMMIT` or a first write, through the real adapter.
    - **Test install variant.** `psycopg` 3.3.6 with the `binary` build (bundled libpq) and `psycopg-pool` 3.3.3, recorded in the qualification note; the extra itself names plain `psycopg`.
12. **The Python AWS KMS key provider** ([#127](https://github.com/redact-secret/redact-secret-vault/issues/127)). `redact_secret_vault.keys.aws_kms` follows `packages/key-provider-aws-kms` where bytes cross: the key reference `aws-kms:<full key ARN>` (an alias or a bare key id is refused), the profile `aws-kms-envelope-v1`, and the encryption context `{"rsv:ctx": base64url(SHA-256("rsv-kms-context-v1" 0x00 || lp16(namespace) || lp16(tenant) || lp16(captureId))), "rsv:v": "1"}` plus opt-in labels, so a data key wrapped by one provider unwraps in the other. What Python forced:
    - **Synchronous client, worker thread.** `boto3` is synchronous, so each call is `asyncio.to_thread` bounded by `call_timeout_ms` (default 5000). A thread cannot be cancelled: a call given up (timeout or task cancellation) is still running, and its outcome is dropped with its exception retrieved, so no warning or unretrieved exception follows. The provider never retries and never sets a client option; the application builds the client with its own `connect_timeout`, `read_timeout`, and retry mode.
    - **Not importing `boto3`.** The module needs the `aws-kms` extra to be installed (`require_extra`) but imports no part of `boto3` or `botocore`, and none of `cryptography`: error classification reads only the exception's class name, the `Code` of its `response`, and an HTTP 429, and the digest is `hashlib`. The module does not import `redact_secret_vault.crypto` (whose package initializer needs `cryptography`), so the `aws-kms` extra works without the `crypto` extra.
    - **Plaintext handling.** `boto3` returns `Plaintext` as immutable `bytes`, which Python cannot overwrite. The provider copies it into a `bytearray` the caller overwrites and holds no reference to the `bytes`. A late response is dropped, not overwritten.
    - **The opt-in cache** keeps the JavaScript bounds (at most 10 000 entries, at most 300 000 ms, per-tenant bound) and uses the monotonic clock by default, so it cannot be extended by setting the system clock back. A clock reading that is not a number, or goes backwards, expires an entry.
    - **`KEY_ABORTED` is never raised** (decision 5): there is no abort signal, and task cancellation propagates as `CancelledError`.
    - **`botocore` at `DEBUG` logs the data key.** Measured with a real key, not assumed: `botocore.parsers` writes the response body, which holds `Plaintext` in base64, and the key ARN. The provider itself logs nothing and sends no identifier in clear, so no namespace, tenant, or capture identifier is in those records. An application must not enable `DEBUG` for `botocore`, `boto3`, or `urllib3` where the records reach any sink.

## Measured seal and open time

`tests/test_crypto_max_capture.py` seals and opens captures at the limits of the format and prints the times with `-s`. Three runs on 2026-10-01, Apple arm64, Darwin 25.5, CPython 3.12.14, `cryptography` 50.0.2, local key provider, one run per process after the first call, median of five repetitions each. Whole-call wall time, including key derivation, nonce draw, and payload encoding or decoding. Not a benchmark claim for any other machine.

| Capture | Seal | Open |
| --- | --- | --- |
| 1 entry of 1 MiB (largest value) | 0.4 ms | 0.4 ms |
| 1024 entries of 1 KiB (most entries) | 17 to 18 ms | 17 ms |
| 1024 entries of 8 KiB (default value limit, 8 MiB) | 19 to 20 ms | 21 ms |
| 64 entries of 1 MiB (64 MiB) | 20 to 22 ms | 20 ms |

The first call in a process was up to about 10 ms slower than these. The cost is dominated by per-entry work (about 16 µs each for the HKDF object, the AES-GCM context, and the encoding), not by the cipher, which is far faster than the interpreter overhead. Inline execution therefore blocks the event loop for at most a few tens of milliseconds on this machine. Decision 7 stands unless a measurement on the target hardware, with the store's real `max_create_bytes`, shows a stall the application cannot accept. A cooperative `await asyncio.sleep(0)` between entries would bound the stall without a thread and keeps the cancellation rule; it is not added until such a measurement asks for it.

## `verify_vectors.py`

[`conformance/persistent/v1/verify_vectors.py`](../../conformance/persistent/v1/verify_vectors.py) exists. It rebuilds the `entryId`, session tag, request digest, entry key, AAD, payload, envelope, and local-wrap vectors from the specification with the standard library, checks AES-256-GCM with `cryptography`, and checks that the `negative.open` cases of code `RECORD_INTEGRITY` do not authenticate. It does not decode a negative envelope or payload and does not test any shipped Python code.

It is kept, unchanged, as the independent oracle: it shares no code with either implementation, so a mistaken reading of the specification would have to be made three times. The Python package tests are a separate run: they feed the same `vectors.json` to the code that ships in the wheel, including every negative case.

## Consequences

- The wheel gains modules `persistent`, `crypto`, `stores.postgres`, and `keys.aws_kms`. The last three raise `ImportError` naming the extra when the dependency is missing.
- Python persistence stays "not supported" in every README, status table, and package description until issue #128.
