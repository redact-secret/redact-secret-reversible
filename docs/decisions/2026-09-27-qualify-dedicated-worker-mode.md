# Qualify optional dedicated-Worker mode and its failure behavior

> **Accepted 2026-09-27** for `@redact-secret/vault`'s optional Worker mode ([#14](https://github.com/redact-secret/redact-secret-vault/issues/14), depends on [#12](https://github.com/redact-secret/redact-secret-vault/issues/12)/[#13](https://github.com/redact-secret/redact-secret-vault/issues/13)). This does not change, weaken, or extend what the main-thread mode already established ([qualification record](../research/qualification-0.1.0-alpha.1.md)); it is a second, separately qualified mode consumers opt into explicitly.

## Context

[docs/specs/in-memory-security.md](../specs/in-memory-security.md) section 5 ("Optional Worker isolation") and the [threat model](../specs/threat-model.md)'s "Dedicated Worker — proposed, not supported" row already named the open work before any code existed: validate message shape/operation inside the Worker, never expose a dump/export operation, keep the mapping Worker-owned, terminate on disposal, and never fall back to main-thread memory silently. Gate V (the issue roadmap) requires a runtime's own conformance runner and end-to-end packaging to pass before it is marked supported, and states plainly that "Worker is an optional separately qualified mode, not an implicit upgrade."

A dedicated Worker changes *where* the mapping lives (a separate JavaScript agent, not reachable through direct main-thread object access) but not *who* can operate on it: a same-page script that can reach the `Worker` object can still send it a request through the same protocol a legitimate caller uses, and can still observe whatever that protocol legitimately returns. [MDN: Using Web Workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers) and the [OWASP HTML5 Security Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) describe the same boundary: a Worker is an isolation mechanism against *accidental* reach and against a class of memory-scraping/introspection paths, not an authentication boundary against a page that is already compromised.

## Decision

- **Worker-owned mapping.** The vault instance — including every retained entry — is created and lives entirely inside a closure private to the Worker's module scope (`packages/vault/src/worker-host.ts`). It is never assigned to a global, to `self`, or to any value a posted message can reach. The only way to affect it is the validated protocol below.
- **A validated message protocol, not a bare RPC pass-through.** Every message carries a fixed `kind` discriminator and version (`packages/vault/src/worker-protocol.ts`). Both the host and the client parse and reject — never coerce — anything that does not match one of exactly five operations (`capture`, `restore`, `revoke`, `stats`, `dispose`) with exactly the allowed keys for that operation. `__proto__`, `constructor`, and `prototype` are rejected unconditionally as keys, regardless of what an operation's schema would otherwise allow. There is no `dump`, `listSecrets`, `export`, or other bulk-read operation in the protocol; there never was one to accidentally leave in.
- **Explicit error, never silent fallback.** `createWorkerVault` (the main-thread client) never creates or falls back to an in-process vault. If the Worker fails to start (for example its own CSP blocks WebAssembly compilation), errors, is terminated, or does not answer within a timeout, the caller's promise rejects with a fixed `VaultError` — `WORKER_PROTOCOL_VIOLATION` for a message that does not match the protocol, `WORKER_UNAVAILABLE` for a Worker that did not/cannot respond, or the Worker's own reported failure code (for example `CORE_FAILURE`/`INITIALIZATION_FAILED`). A consumer that wants a main-thread fallback must request it as a separate, explicit choice; the library never makes that substitution for them.
- **A different, not a superset, API shape.** Worker mode does not implement the synchronous `Vault` interface. `WorkerVault` mirrors its five operations but every one returns a `Promise`, because every one is a message round trip. `policy`, `eligible`, and `displayFormatter` are functions and cannot cross `postMessage`'s structured-clone boundary (and running main-thread-supplied code inside the Worker would defeat the isolation this mode exists to provide), so Worker-mode capture accepts only `release`, `maxUses`, `unredacted`, and `ruleset`. Passing one of the unsupported options throws `INVALID_ARGUMENT` synchronously, before anything is sent.
- **Physically separate transport code.** `worker-client.js` (main thread) and `worker-host.js` (Worker) are separate packed files that do not import each other, and neither is reachable from the package's main `"."` entry. Plain `import "@redact-secret/vault"` gains no `postMessage`/`BroadcastChannel`/`SharedWorker` capability; only a consumer who explicitly imports `"@redact-secret/vault/worker"` and/or `"@redact-secret/vault/worker/host"` opts into Worker mode. `qualification/check-boundaries.mjs` enforces both properties on the packed artifact, not just the source tree.

## Guarantee boundary

Worker mode's guarantee is structural isolation from *ordinary* main-thread code: application code that only holds a `WorkerVault` handle cannot enumerate, dump, or directly read the mapping, and cannot make the Worker execute anything outside the five defined operations. It is explicitly **not** an authentication or XSS-resistance boundary: a main thread that is itself compromised (for example by XSS) still has whatever `Worker`/`MessagePort` reference the legitimate application code has, and can therefore still call `capture`/`restore` through the same protocol and observe their results, exactly as legitimate code can. The [hostile-main-thread test](../../packages/vault/test/worker-suite.js) exists to demonstrate both halves of this: that out-of-protocol requests (unknown operations, malformed envelopes, extra keys, prototype-pollution-shaped payloads) are rejected explicitly and do not crash the Worker, and that in-protocol requests still succeed — Worker mode narrows the attack surface, it does not remove it. Main-thread-only and Worker-mode guarantees are documented separately (README, threat model, in-memory-security spec) precisely so they are not conflated.

## Consequences and alternatives

- **Packaging.** Worker mode is a genuinely optional, additively-packaged mode: a consumer who never imports `"@redact-secret/vault/worker"` builds and ships exactly what alpha.1 already qualified, unchanged. This is verified on the packed tarball, not asserted from the source tree.
- **CSP.** A dedicated Worker created with `new Worker(url)` is its own Trusted Types sink (`TrustedScriptURL`), distinct from the `<script src>` sink main-thread qualification exercises, and a Worker's own effective CSP is governed by *its own* script response headers when present, not silently inherited from the creating document. Consumers deploying Worker mode under `require-trusted-types-for 'script'` need a `trusted-types` policy (for example a narrow `"default"` policy) and an explicit `worker-src` directive; qualification evidence exercises both, including the case where `worker-src` denies Worker creation entirely.
- **Not chosen: sharing one vault instance's serialized state between main thread and Worker.** That would require exposing a mapping-shaped snapshot to the main thread at some point, defeating the isolation goal.
- **Not chosen: a synchronous-looking Worker-mode API (for example via `Atomics.wait` and `SharedArrayBuffer`).** That would need `SharedArrayBuffer` and cross-origin-isolation headers most consumers do not control, and would materially complicate the failure-mode story (a blocked main thread cannot easily observe or time out a hung Worker). The asynchronous `WorkerVault` shape is a deliberate, visible difference from `Vault`, not a limitation to hide.
- **Residual risk carried forward unchanged from the main-thread mode:** undetected secrets, a model relocating a valid token within a granted field, memory erasure, and DevTools/debugger inspection are unaffected by which thread holds the mapping. See the [threat model](../specs/threat-model.md)'s residual-risk table.

## Verification before acceptance

Real dedicated Workers in Chromium, Firefox, and WebKit (via Playwright), under a strict CSP served per-response (`default-src 'none'`, a pinned `script-src`, `worker-src`, and Trusted Types), covering: capture/restore parity with the documented contract; a non-cloneable capture option rejected client-side before any message is sent; five distinct out-of-protocol requests (unknown op, wrong `kind`, an unexpected extra key, a `__proto__`-bearing payload, and a non-object message) each rejected explicitly, with the Worker still serving legitimate requests afterward; no fixture plaintext in a protocol-violation reply; a negative CSP control where `worker-src 'none'` denies Worker creation entirely and the client rejects rather than falling back; and a second negative control where the Worker is created but its own CSP forbids WebAssembly, and vault creation inside it fails closed with the same `CORE_FAILURE`/`INITIALIZATION_FAILED` the main-thread mode already reports. See `qualification/worker.mjs`.

## Resolved choices (Worker mode, `@redact-secret/vault`)

- **Transport.** `postMessage`/`message` events between a main-thread client (`createWorkerVault`) and a Worker-side host (`startVaultWorkerHost`). A `MessagePort` satisfies the same minimal structural interface, so a consumer may route through one instead of a bare `Worker`.
- **Protocol version.** Messages carry `v: 1`. A future incompatible protocol change bumps this; both sides already reject an unrecognized version rather than guess at compatibility. (Bumped to `v: 2` by [#39](https://github.com/redact-secret/redact-secret-vault/issues/39) under the [PII retention and activation ADR](2026-09-27-decide-pii-retention-and-activation-ownership.md) §3 "Worker mode".)
- **Error codes.** Two additions to the shared `VaultErrorCode` set: `WORKER_PROTOCOL_VIOLATION` (a message did not match the protocol) and `WORKER_UNAVAILABLE` (the Worker did not respond, errored, or was terminated). Both carry the same fixed-message, no-payload shape every other vault error already does.
- **Timeout.** `createWorkerVault` accepts an optional `timeoutMs` (default 15000) applied to the initial readiness handshake and to each individual call. There is no default-forever wait; a hung or hostile Worker fails a pending call explicitly rather than leaving a caller waiting indefinitely.
- **Disposal.** `WorkerVault.dispose()` disposes the Worker-held vault (a round trip) and then fails fast locally on further calls; `WorkerVault.terminate()` calls the underlying `Worker.terminate()` immediately and fails every pending and future call with `WORKER_UNAVAILABLE`.
- **Scope.** This decision qualifies a browser dedicated Worker specifically. It does not qualify `SharedWorker`, a Service Worker, or Node.js `worker_threads` (whose message-port API differs from the `postMessage`/`self` surface qualified here); none of those are claimed supported by this change.

## Evidence

`packages/vault/test/worker-suite.js` (15 cases: 3 parity, 1 protocol pre-send validation, 5 hostile-message rejections, 1 leakage check on a hostile reply, plus 4 browser-runner-added CSP/asset checks) passes 15/15 in Chromium 153.0.8010.12, Firefox 155.0, and WebKit 26.6 against the packed tarball with the pinned `@redact-secret/core@0.1.0-beta.9`, alongside the unchanged 65/65 main-thread suite (`qualification/browser.mjs`) and 61/61 Node.js suite (`qualification/node.mjs`) on the same commit. `qualification/check-boundaries.mjs` additionally asserts the packed artifact's main `"."` entry never imports Worker-mode code and that `worker-client.js`/`worker-host.js` do not import each other. Reproduce with `npm run qualify:worker` (`BROWSERS=chromium,firefox,webkit`); reports land in `.qualification/reports/`.
