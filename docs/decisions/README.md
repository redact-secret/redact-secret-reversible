# Decisions

Decision records document durable product and security boundaries. Their status describes a design decision, not an implemented or released feature.

| Record | Status | Question answered |
| --- | --- | --- |
| [Separate the reversible boundary](separate-reversible-boundary.md) | Accepted | Which repository owns retention and restoration? |
| [Decouple typed placeholders from restoration](decouple-typed-placeholders-from-restoration.md) | Accepted (note added 2026-09-28 for core beta.10 PII types) | Does a typed label carry restore identity or authority? |
| [Define restore authority and lifecycle](restore-authority-and-lifecycle.md) | Accepted principles; implementation open | Which checks are invariant, and which choices belong to the application? |
| [Name vault packages and preserve a language-neutral server contract](name-vault-packages-and-language-contract.md) | Accepted names and boundaries; delivery open | How do browser, server, and persistence packages relate across languages? |
| [Bind issued tokens to approved output](bind-issued-tokens-to-approved-output.md) | Accepted for the in-memory vault; server binding open | How are issued identities, model copies, and destination paths handled? |
| [Gate capture on core actions](gate-capture-on-core-actions.md) | Accepted for whole-input capture; streaming open | What do `block`, `redact`, `warn`, and `allow` mean for capture and outbound use? |
| [Define restore transaction boundary](define-restore-transaction-boundary.md) | Accepted for the single-process in-memory vault; stores open | What can be atomic across validation, budgets, revocation, and delivery? |
| [Define the server authority interface and reference policy examples](define-server-authority-interface.md) | Accepted for the interface contract; implementation open | What must a server authority layer resolve, check, deny, and audit, without mandating an identity provider? |

| [Implement `@redact-secret/vault-server`'s in-memory backend and linearization point](implement-vault-server-in-memory.md) | Accepted | How does #16's implementation resolve the linearization point, storage shape, revocation memory, and audit split the interface ADR left open? |
| [Define the persistent store, encryption, and key ownership contract](define-persistent-store-contract.md) | Accepted 2026-09-27 for the interface contract; partly superseded 2026-10-01 by the record below | What must a persistent store guarantee for atomicity, logical TTL, tenant isolation, AEAD metadata binding, key rotation, backup/deletion, and failure behavior, without mandating a vendor? |
| [Supersede the persistent store contract with ciphertext-only stores and independent key providers](supersede-persistent-store-contract.md) | Accepted 2026-10-01 after independent design review ([#104](https://github.com/redact-secret/redact-secret-vault/issues/104), [#105](https://github.com/redact-secret/redact-secret-vault/issues/105), [#107](https://github.com/redact-secret/redact-secret-vault/issues/107)). Implementation review pending | Who owns authorization, encryption, keys, and storage in a persistent vault; what is atomic; what a retry may return; what deletion can promise? The interfaces and bytes are in the [persistent vault specification](../specs/persistent-vault.md) |
| [Support two SQLite drivers in `@redact-secret/store-sqlite`, injected by the application](choose-sqlite-driver.md) | Accepted 2026-10-01 for the driver choice only; the SQLite profile is not qualified ([#130](https://github.com/redact-secret/redact-secret-vault/issues/130)) | How does the SQLite store get a driver, and which Node.js releases may use `node:sqlite`? |
| [Decide PII retention eligibility and core PII activation ownership](decide-pii-retention-and-activation-ownership.md) | Accepted. Implemented and published in `0.1.0-alpha.2` on 2026-09-28 ([#44](https://github.com/redact-secret/redact-secret-vault/issues/44), [#55](https://github.com/redact-secret/redact-secret-vault/issues/55)): main thread and `vault-server` ([#38](https://github.com/redact-secret/redact-secret-vault/issues/38)), Worker ([#39](https://github.com/redact-secret/redact-secret-vault/issues/39)), Python ([#40](https://github.com/redact-secret/redact-secret-vault/issues/40)). Qualified against core `0.1.0-beta.10` with PII off and on ([#42](https://github.com/redact-secret/redact-secret-vault/issues/42), [record](https://github.com/redact-secret/redact-secret-vault/blob/0db9a33a654704f1afad9388f5fdf0cf403a6b01/docs/research/qualification-core-0.1.0-beta.10.md)) | Are `pii_` findings retained without a PII-specific opt-in, what happens to `warn` PII, and who initializes the core's realm-global PII selection? |

`@redact-secret/vault` 0.1.0-alpha.1 implements the three records accepted on 2026-09-27 for its in-memory, whole-input scope. Their *Resolved choices* sections fix the token grammar, default use count, limits, linearization point, and (for Worker mode) the message protocol, and cite the qualification evidence. The server authority interface ([#15](https://github.com/redact-secret/redact-secret-vault/issues/15)) is decided as a contract, generalizing that same model with principal/tenant/purpose. Worker mode (V4, [#14](https://github.com/redact-secret/redact-secret-vault/issues/14)) is implemented and qualified. `@redact-secret/vault-server` 0.1.0-alpha.1 ([#16](https://github.com/redact-secret/redact-secret-vault/issues/16)) is its first concrete implementation, with an in-memory backend built on `@redact-secret/vault`. A research-grade Python implementation also exists ([#17](https://github.com/redact-secret/redact-secret-vault/issues/17), `packages/vault-py`, distribution `redact-secret-vault` since [#56](https://github.com/redact-secret/redact-secret-vault/issues/56) — see the dated note on the [naming decision](name-vault-packages-and-language-contract.md), in-memory storage, capture through a documented Node.js service boundary to the core — no native Python core distribution exists; see the archived [Python server integration record](https://github.com/redact-secret/redact-secret-vault/blob/0db9a33a654704f1afad9388f5fdf0cf403a6b01/docs/research/python-server-integration-2026-09-27.md)). The persistent-store contract ([#19](https://github.com/redact-secret/redact-secret-vault/issues/19)) was decided as a contract and never implemented as written: its store interface, key-provider shape, per-entry atomicity, plaintext replay, and deletion promise are replaced by the superseding record. That record is implemented on `main`, unpublished: `@redact-secret/vault-contracts`, `@redact-secret/vault-crypto` with the local key provider, `@redact-secret/vault-conformance`, `@redact-secret/store-memory` (non-durable, tests only), the persistent profile of `@redact-secret/vault-server`, `@redact-secret/store-postgres` ([#20](https://github.com/redact-secret/redact-secret-vault/issues/20)), and `@redact-secret/key-provider-aws-kms` ([#113](https://github.com/redact-secret/redact-secret-vault/issues/113)). The [qualification record](../research/qualification-persistence-0.1.0-alpha.1.md) names what was tested: Node.js 22 with PostgreSQL 17.11 as a single primary or a primary with one synchronous standby. The record's own header still says no package implements it; that sentence predates the implementation. Opt-in PII detection in core `0.1.0-beta.10` is decided as a contract ([#45](https://github.com/redact-secret/redact-secret-vault/issues/45)), implemented on every surface, and qualified with PII off and on ([#42](https://github.com/redact-secret/redact-secret-vault/issues/42)), and published in `0.1.0-alpha.2` ([#44](https://github.com/redact-secret/redact-secret-vault/issues/44)). A `pii_` finding is never retained without a PII-specific allowlist. The application, not the vault, owns the core's realm-global PII activation. The vault stays compatible with beta.9 by feature detection. Still open for persistence: the independent implementation review and the first publication ([#112](https://github.com/redact-secret/redact-secret-vault/issues/112)); Python persistence ([#115](https://github.com/redact-secret/redact-secret-vault/issues/115), [plan](../plans/python-persistence-parity.md) only); any backend other than PostgreSQL ([#114](https://github.com/redact-secret/redact-secret-vault/issues/114); DynamoDB and Redis are [research](../research/persistent-backend-capabilities.md) only, and `@redact-secret/store-sqlite` is implemented with a [partial record](../research/qualification-store-sqlite-0.1.0-alpha.1.md) and no support claim, [#130](https://github.com/redact-secret/redact-secret-vault/issues/130)); returning recovered captures to service, payload re-encryption, a store-enforced quota, and the other open questions of specification §12. Still open elsewhere: cross-language JS/Python conformance documentation ([#18](https://github.com/redact-secret/redact-secret-vault/issues/18)), arbitrary-text restore semantics, streaming, and Rust/Go threat models. The [threat model](../specs/threat-model.md) states each mode's boundary. See the archived [security research](https://github.com/redact-secret/redact-secret-vault/blob/0db9a33a654704f1afad9388f5fdf0cf403a6b01/docs/research/security-foundations-2026-09-27.md) and the [pre-implementation plan](https://github.com/redact-secret/redact-secret-vault/blob/0db9a33a654704f1afad9388f5fdf0cf403a6b01/docs/plans/pre-implementation.md).
