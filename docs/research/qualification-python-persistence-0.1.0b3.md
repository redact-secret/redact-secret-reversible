# Qualification record: Python persistence, `redact-secret-vault` (tree of 0.1.0b3)

**Status:** record of what was run for the Python persistence modules in this tree. It is the document the [plan](../plans/python-persistence-parity.md) (section 6) and the [decision record](../decisions/python-persistence-api-and-packaging.md) mean by "support is stated only by the qualification record". Tracking issue: [#128](https://github.com/redact-secret/redact-secret-vault/issues/128), under epic [#4](https://github.com/redact-secret/redact-secret-vault/issues/4), plan handoff 10.

**Python persistence is not supported.** Two gates below are not passed in full (G5 at the bridge's default settings, and G9; G6 is passed for the PostgreSQL path with the local key provider and not for the AWS KMS provider: see [section 2](#2-result-by-gate)), so every Python persistence statement outside this record keeps the wording "not supported" or "research". A row below is evidence for exactly the versions, backend, topology, operating system, and key provider it names. Anything not named is not qualified. A skipped test is not a pass, and a run that was not made is listed as **NOT RUN**.

## 1. Scope and date

Recorded 2026-10-01; gates G5, G6, and G9 were run again on 2026-10-02 (sections 4.5, 4.6, 4.9, and the new 4.10), and the sections that name them were amended in place, so this stays the one record. G5 was run a third time on 2026-10-02 after the bridge changes of [#128](https://github.com/redact-secret/redact-secret-vault/issues/128) (branch `fix/128-bridge-hardening`; sections 4.9 and 4.10 say what ran and what changed). Every identifier, key, token, and password used in these runs was synthetic. The one real service used is AWS KMS in `us-east-1` with two symmetric test keys created for the run, scheduled for deletion afterwards (section 4.2); no ARN, account identifier, or credential is written here.

In scope: the Python persistent modules of the distribution `redact-secret-vault` as built from this tree: `redact_secret_vault.persistent` (contracts, canonical encoding, digests, the reference `store_memory`, the persistent server profile), `redact_secret_vault.crypto` (record crypto and the local key provider), `redact_secret_vault.stores.postgres` (PostgreSQL over `psycopg` 3), and `redact_secret_vault.keys.aws_kms` (AWS KMS over `boto3`).

Not in scope: performance beyond the measurement in the [decision record](../decisions/python-persistence-api-and-packaging.md) and the bridge measurements of section 4.10; backends other than PostgreSQL; browser or Worker modes; Rust and Go. The Node.js core bridge is **in scope of section 4.10 only**, as a component that was measured and attacked; the [decision](../decisions/limit-python-persistence-claim-to-a-supplied-core-client.md) that no Python persistence statement includes it as a qualified component stands.

**Version of the artifact.** Every run below used the working tree or the wheel built from it. The wheel reported `0.1.0b3` because `pyproject.toml` had not been changed. It is not the published `0.1.0b3` on PyPI, which has none of these modules: `pip install redact-secret-vault==0.1.0b3` installs the in-memory server only. These modules shipped in `0.1.0b4`, behind extras, not supported; the verdicts below are unchanged by that.

**Key provider, against real AWS KMS.** `pytest tests/test_aws_kms_real.py` with `RSV_KMS_TEST_KEY_ARN` and `RSV_KMS_TEST_OLD_KEY_ARN` set to two symmetric keys of one account in `us-east-1`, the default credential chain through a named profile. - a different context fails `KEY_INTEGRITY`, for a key made by either side and unwrapped by either side;
- a key wrapped by the old key and rewrapped to the active key by Python unwraps in JavaScript, and a JavaScript rewrap is unwrapped by Python;
- a disabled key fails `KEY_UNAVAILABLE` (visible to `Decrypt` after 61 s on this run, KMS being eventually consistent) and works again when enabled;
- no namespace, tenant, or capture identifier appears in clear in any request context of `GenerateDataKey`, `Decrypt`, or `ReEncrypt`; the context is the digest and a version;

The JavaScript counterpart is assessed in [aws-sdk-v3-logger-and-key-material.md](aws-sdk-v3-logger-and-key-material.md).

56 further tests of the provider run against a fake client shaped like `boto3` and need no credentials (they run in CI); they are not interoperation evidence. Throttling was not provoked against the real service. The two keys were scheduled for deletion (7-day window) after the run.

### 4.10 G5 Bridge qualification

**What was qualified, and by what.** `NodeCoreBridge` (`core_client.py`), `boundary/core_bridge.mjs`, and the pinned `@redact-secret/core` `0.1.0-beta.12`, as the persistent server uses them: one child process per bridge, newline-delimited JSON on its pipes, the whole input in each request. The tool is `tests/bridge_qualification.py` (not in the wheel; `python tests/bridge_qualification.py --help`); `tests/test_bridge_qualification.py` runs its quick form in the suite, `tests/test_core_integrity.py` and `tests/test_bridge_process.py` hold the unit cases, and the persistent-server cases are in 4.6. **Two runs.** The first run (2026-10-02, before the changes of #128) closed the three gaps of the [decision](../decisions/limit-python-persistence-claim-to-a-supplied-core-client.md) and found two criteria **not met** (an error code reported by the child was copied into the exception unvalidated; a core changed on disk that reports the pinned version string was accepted, with strict `xfail` tests pinning both) and three limits measured (a queue not bounded by `timeout_s`, scans on the event loop's default executor, a spawn per request for a core that cannot load). - **Plan 6.2, bridge qualification.** Its text names three gaps: an adversarial protocol run, fuzzing of the frame parser, and a statement of supported operating systems. **All three are closed for the cells above** (78 cases, 2,000 and 100,000 and 20,000 fuzzed cases, the cells stated), with no violation. - **This record's own criteria** (added by the first run; not weakened here). Every one is **met in the cells run, except plaintext retention**: it is **not met with the default `max_scans_per_process` of 10,000**, because the child keeps a copy of an earlier scan's secret in its memory until it exits (2 and 3 copies here, unchanged after 6,100 further scans), and it is **met with `max_scans_per_process=1`**, which kills the child inside the call. That setting costs a new child per scan: **9.9 scans per second per bridge with the integrity pin on Linux (17.7 without) and 12.6 on macOS (11.9 without)**, against 1,100 to 4,100 at the default on the same hosts, so the setting is for workloads that can pay it, with one bridge per worker. The throughput ceiling is a measurement: 350 to 4,100 scans per second per bridge depending on the host and its load.
- **Why the gate is still not passed in full.** The bridge is not named qualified at its default settings for any cell, because a criterion of the record is not met there. Whether to name it for the cells run with `max_scans_per_process=1`, with the integrity pin, is the maintainer's decision; this record does not, and the [decision](../decisions/limit-python-persistence-claim-to-a-supplied-core-client.md) (decision 1) is unchanged. **Not adopted, for the maintainer:** (a) keep the default of 10,000 for the in-memory server, whose published behavior must not change, and make the persistent profile's claim carry a **documented requirement** (`max_scans_per_process=1`, or a `CoreClient` the application qualifies) rather than a changed default; (b) alternatively, have `create_persistent_server_vault` refuse a `NodeCoreBridge` whose `max_scans_per_process` is above 1 unless the application passes an explicit acknowledgement, which would change the public behavior of the persistent profile and needs its own decision; (c) in either case the claim for the bridge names exactly the cells above, the pinned core release, and the limits of the integrity pin (the node executable, the bridge script, and a hash-to-import race are outside it).
- **Not run, and so not claimed:** Windows, musl, native Linux x86-64, any other Node.js version, the heavy sections on Node.js 20 and 24, a memory scan on macOS, the 448 MiB request on Node.js 20 and 24, and any core other than `0.1.0-beta.12`.

## 7. What this record supports

This record is the only document that may state support for a Python persistence cell, and it states **none**: [section 2](#2-result-by-gate) shows gates that are not passed in full. What the record lets other documents say, and no more:

- The Python distribution's source tree contains persistent modules (`persistent`, `crypto`, `stores.postgres`, `keys.aws_kms`) behind the `crypto`, `postgres`, and `aws-kms` extras. They ship in `0.1.0b4`, behind extras, not supported. The published `0.1.0b3` does not contain them.
- Against the cells named in section 3, and only those, these runs passed: the shared vectors; mixed-language interoperation with the JavaScript persistent server on one PostgreSQL 17.11 database, in both directions, including lifecycle and negative cases; the schedule corpus through a Python driver against the Python reference store and the Python PostgreSQL adapter; the two-process cases with real operating-system processes on one host; capture parity with the in-memory server and with the JavaScript persistent server on the shared corpus; the diagnostics runs listed in 4.6; and the 31 named mutation controls.
- One data key wrapped by the JavaScript AWS KMS provider was unwrapped by the Python provider, and one wrapped by the Python provider was unwrapped by the JavaScript one, against real keys in `us-east-1`. One run, one region, one key spec.
- The core bridge is not named qualified. It was attacked and measured in 4.10 twice: the three gaps of plan 6.2 are closed for the cells there, every criterion added by the record is met in them except plaintext retention (not met at the default `max_scans_per_process`, met at 1), and the throughput ceiling is measured. A capture in these runs went through `NodeCoreBridge` as a test fixture. Any deployment claim is for an application-supplied, separately qualified `CoreClient` ([decision](../decisions/limit-python-persistence-claim-to-a-supplied-core-client.md)).
- Not run, so not stated: Windows and macOS CI, Linux x86-64 beyond the GitHub-hosted subsets and the emulated subset of 4.9, free-threaded or PyPy interpreters, Python 3.10 for the persistent modules (the modules refuse to import on it, and the tests are not collected), a PostgreSQL with a synchronous standby, failover, a connection pooler, managed PostgreSQL, two hosts, power loss, throttling by AWS KMS, the KMS provider under the server-level leak run, any region or key type but the one named, and the CI jobs on any commit after `cb54581`.
- At-rest statements are about the store. They say nothing about plaintext that lives in the Python process, in the bridge's child (4.10 measured it), in logs of libraries the application enables (section 4.2 shows `botocore` at `DEBUG` writing the data key; 4.6 shows `psycopg` and `asyncio` at `DEBUG` writing none), or in memory the interpreter cannot clear (plan 3.6).
